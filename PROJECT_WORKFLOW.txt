================================================================================
 1. WHAT THE SYSTEM IS
================================================================================

 A trip planner for Myanmar, delivered as three tiers:

   Browser SPA  ->  Java HTTP gateway  ->  Java RMI service
   (no build)       (java.net.http +         (business logic,
                     com.sun.net.httpserver)  Java serialization)

 Key properties:

   * Build = javac only. No Maven, Gradle, npm, or database is required to run.
   * The catalogue is code: 9 destinations and 66 attractions live in
     DataStore; the 82 hotels are generated from data/hotels.json into
     HotelCatalogue.java (real properties from the Wikivoyage sleep guides)
     and registered at startup.
   * Persistence is two Java-serialized files: data/bookings.ser and
     data/partners.ser.
   * Payments are simulated. No wallet, bank, or network call is made.
   * The marketplace (shop) is entirely client-side. It has no server side.
   * PostgreSQL exists as an optional "Phase 1B" track (db/, shared/), and is
     NOT used by the running RMI service yet.

   TripException     business error surfaced over RMI

   ServerMain        creates/uses the RMI registry, binds TripService
   TripServiceImpl   itinerary, booking, payment, partner accounts/properties

   DataStore         in-code catalogue; also holds partner hotels in memory
   PartnerData       serializable root of data/partners.ser

 DATABASE TRACK (optional, unused at runtime)
   shared/Db, MigrationRunner, SeedRunner, CatalogueSeed, db/*.sql, docker-compose

 3. BOOT WORKFLOW
================================================================================

 3.1 One process (the normal demo)

   run.bat
     |
     |-- if out\com\mmtrip\client\WebMain.class is missing -> build.bat
     |
     `-- java -Dmht.demo=true -cp "out;lib/*" com.mmtrip.client.WebMain --embedded
            |
            1. main() parses args and defaults host=127.0.0.1, rmiPort=1099,
               httpPort=8080, embedded=true, openBrowser=true, webRoot=./web
               (WebMain:55-78)
            2. embedded -> ServerMain.start(1099):
                 - reuses a registry on 1099 or creates one
                 - binds "MyanmarTripService" -> new TripServiceImpl()
                 - prints [RMI] Created registry / Bound
            3. TripServiceImpl constructor loads state:
                 - DataStore builds 9 destinations and 66 places
                 - HotelCatalogue.register() loads the 82 generated hotels
                   (data/hotels.json -> tools/generate_hotel_catalogue.py)
                 - loadPartners()  <- data/partners.ser   [PARTNER] Loaded ...
                 - loadBookings()  <- data/bookings.ser   [DATA] Loaded 7 booking(s)
                 - if demo mode: seedDemoPartner() (partner@mstp.demo / partner123,
                   two sample Bagan properties, only if missing)
            4. connect(host, 1099): RMI lookup with up to 20 retries x 500 ms,
               so a separately started server is also acceptable (WebMain:127-144)
            5. HttpServer.create on 8080; if busy, try 8081..8099 (20 attempts),
               print "[WEB] Port 8080 is busy - trying 8081..." (WebMain:90-105)
            6. 8-thread fixed pool, then:
                 "Myanmar Trip Planner is live -> http://localhost:8080"
            7. Desktop.browse() opens the default browser unless --no-browser

 3.2 Two-process mode (shows the real remote split)

   run-server.bat   -> registry + TripService only          (port 1099)
   run-client.bat   -> RMI lookup + web gateway             (port 8080+)
   Embedded mode simply calls the same ServerMain.start() in-process.

 3.3 Build

   build.bat / build.sh
     tools/fetch-deps.*    downloads PostgreSQL driver + HikariCP + SLF4J (lib/)
     dir /s /b src\*.java > sources.txt
     javac -encoding UTF-8 -cp "lib/*" -d out @sources.txt
     del sources.txt
   JDK 17+ is enough (verified on JDK 25). Output: out/com/mmtrip/**/*.class

 3.4 Useful flags

   --embedded / -e        start the RMI server in-process
   --no-browser           do not open a browser
   --http-port 9090       first HTTP port to try (then 9090..9109)
   --rmi-port 1100        RMI registry port (server must match)
   --host 192.168.1.20    remote RMI host
   --web <path>           different static root
   -Dmht.demo=true        seed the demo partner account (or MHT_DEMO=true)

     |  wrap(): assigns req_<8 hex> request id, logs method/path/status/ms
     |          [REQ] req_1e251992 GET /api/hotels 200 33ms
     |  guard(): enforces the HTTP method (405 otherwise), reads the body,
     |           converts TripException -> 400 {"error":"..."}
     v
   RMI (JRMP) -> TripService implementation        (TripServiceImpl)
     |
     |-- ItineraryEngine     planning + costing
     |-- DataStore           catalogue + partner hotels (in memory)
     `-- data/*.ser          bookings and partner accounts, atomic writes
     |
     v
   Serializable models -> Json.write -> HTTP 200 application/json -> app.js

 Static files:
   * "/" or any path without a file extension -> web/index.html (SPA routing)
   * path traversal is blocked; unknown file with an extension is resolved under
     web/ and, if missing, index.html is served (this is why /api/products
     returns the HTML page instead of 404 - there is no such endpoint)
   * Cache-Control: no-store for API, no-cache for static assets
   * Response headers on every reply: CSP, X-Frame-Options DENY, nosniff,
     Referrer-Policy no-referrer, Permissions-Policy (geolocation/mic/camera off),
     HSTS, X-Request-Id                                    (WebMain:455-480)

 External "engine" proxy (optional, not part of this repository):
   MHT_WEATHER_ENGINE_URL   default http://127.0.0.1:8000
   GET  /api/engine/weather/{destinationId}/forecast?latitude=&longitude=&days=&timezone=
   POST /api/route-plan -> /api/v1/planning/trip
   Optional MHT_INTERNAL_TOKEN is sent as X-Internal-Token.
   When it is not running, the UI simply shows "Weather unavailable".

 5.2 The request

   buildPayload()                                  (app.js:1177-1196)
     {
       "destinationIds": ["yangon","bagan"],
       "days":           [1,3],
       "interests":      ["temple","food","sunset"],
       "adults": 2, "children": 1,
       "budget": 900000,
       "hotelTier": "mid",
       "pace": "balanced",
       "startDate": "2026-12-05"
     }
   POST /api/itinerary -> WebMain parses JSON into TripRequest ->
   service.generateItinerary(request)               (WebMain:186)

 5.3 Engine pipeline                              (ItineraryEngine.generate)

   STEP 1  Validate and normalise                    (:40-77)
             destinationIds 1-6, each must exist, duplicates rejected
             nights per destination clamped to 1..10, total > 21 rejected
             adults 1-20, children clamped 0-10, adults+children <= 20,
             budget clamped 0..1,000,000,000
             pace runs through normalize(): an unknown value silently falls
             back to balanced. Legacy "transport"/"style" keys sent in the body
             are ignored, never required.
             interests are lowercased and trimmed into a Set (:79-83)

   STEP 2  Per-day capacity                            (:105)
             pace relaxed -> 4.5 active hours
             pace balanced-> 6.5 active hours
             pace packed  -> 8.0 active hours
           Transport is not an input and has no rate table: there is no mode,
           no per-leg cost and no travel time anywhere in the engine.
           A single destination reports transportRecommendation "NONE"; two or
           more report "UNAVAILABLE" with a note that no route, road or
           timetable data is connected (:111-112, transportNote :357).
           Room count for costing = ceil(travellers / 2), minimum 1.

   STEP 3  Score every attraction of each destination (:117, score 353-367)
             base            rating * 10
             interest match  +14  (interest id == place category)
             sunrise         +6   if bestTime <= 07:00 and "sunrise" chosen
             sunset          +6   if bestTime >= 16:00 and "sunset" chosen
             aliases         +10 for food/nature/culture/adventure
             premium fee      -40 if entry fee > 100,000 (kept as "extra")
             variation jitter +0..4.5 (only on "regenerate")
           (there is no travel-style weighting: only the optional interest
           tags above personalise the ranking)

   STEP 4  Pack each day greedily in score order        (:154-200)
             hoursBudget starts at the pace value
             arrival day: -1.5 h for "Arrive in X, check in, tea"
             transfer day: -3.5 h reserved for the move; the block says the
                           mode and exact travel time are not estimated
             a candidate is skipped when
               pickedHours + candidate.hours > hoursBudget         (:164)
             so a relaxed day takes fewer stops than a packed day

   STEP 5  Schedule chronologically                   (:200-240)
             each stop is placed from its recommended bestTime, after the
             arrival/transfer block, with travel buffers and a lunch block on
             full days; up to five stops per day; dinner is drawn from the
             destination food places

   STEP 6  Add structural days
             first day  -> arrival
             each move  -> transfer morning + check-in afternoon
             last night -> check-out afternoon

   STEP 7  Price the trip                              (:246-266)
             entries = attraction fee * adults + fee/2 * children
             food    = daily rate * (adults + 0.6 * children) * totalDays
             local   = local rate * travellers * totalDays
             transfer= leg cost * travellers * (stops - 1)
             stay    = tier rate * (totalDays-1) * ceil(travellers/2)
                       budget 35,000 | mid 80,000 | luxury 180,000
             total   = stay (hotel nightly price x nights x rooms, summed over
                       the route). Nothing else is priced: no entries, food,
                       local transport or transfers. day.estCost = 0.
                       Each priced stay is also returned in it.stays[].

   STEP 8  Narrative output
             title    "3-Day Bagan Escape" / "Yangon, Bagan & Inle Discovery"
             summary  "N days across ... - a {pace}-paced trip with N
                       hand-picked stops and the stay for each stop planned."
             tips     dress code, cash, layers, transfers arranged locally,
                      destination-specific, hot season, packed pace
             warnings budget delta, over-budget advice (shorten a stop, share
                      rooms, lower stay class), missing-hotel and thin-plan
                      warnings; the total is hotel stays only
             extras   premium places that were auto-excluded

 6. WORKFLOW B - BOOK A HOTEL AND PAY
================================================================================

 6.1 Find a stay

   Hotels view  -> ensureHotels (app.js:2388)
     GET /api/hotels            all hotels, or
     GET /api/hotels?destinationId=bagan
   Filters (renderHotelFilters 2412): class tier, max price, sort by
     price / rating / class.
   Card (hotelCard 2435) shows class, stars, rating, amenities, live rooms-left,
     nightly price, "Listed by ..." for partner properties.

 6.2 Booking form -> room hold

   openBooking (app.js:2548) validates client-side, then
   submitBooking (2618) POSTs:
     { hotelId, guestName, phone, checkIn, nights, rooms }

   Server TripServiceImpl.createBooking (:90-138), synchronized:
     1. hotel must exist in DataStore
     2. guestName trim length >= 2
     3. phone normalised: strip non-digits, 959... -> 09..., 95... -> 0...,
        must match 09\d{7,9}                     (normalizePhone :520-527)
     4. nights 1..30, rooms 1..10, rooms <= hotel.roomsLeft
     5. checkIn must parse as a date and not be in the past
     6. booking id "BK-" + 6 hex of a UUID
     7. total = pricePerNight * nights * rooms
     8. status = PENDING_PAYMENT
     9. hold inventory: hotel.roomsLeft -= rooms
    10. saveBookings() to data/bookings.ser
        -> on write failure: booking is removed and the rooms are released,
           then the error is returned (no silent inconsistency)

   UI then opens the payment modal: "Room held - complete the demo payment."

 6.3 Simulated wallet payment

   openPayment (2645) shows KBZPay / WavePay / AYA Pay, a "Demo / simulated"
   badge, the wallet phone field, and a "Simulate a declined payment" checkbox.
   No PIN field is collected.

   submitPayment (2690) POSTs:
     { bookingId, method, walletPhone, simulateDecline }

   Server TripServiceImpl.pay (:140-198), synchronized:
     1. booking must exist
     2. already CONFIRMED -> error "This booking is already paid."
     3. method must be KPAY | WAVEPAY | AYAPAY
     4. wallet phone normalised with the same rule
     5. simulateDecline -> PaymentResult.success=false, booking untouched
     6. Thread.sleep(900) to mimic a wallet round-trip (UI pending state)
     7. transaction id: KP | WV | AYA + yyyyMMdd + "-" + 6 digits
     8. status -> CONFIRMED, paymentMethod, transactionId, paidAt recorded
     9. saveBookings(); on failure every field is rolled back

   Status machine:

        createBooking
             |
             v
     PENDING_PAYMENT ---- pay success ----> CONFIRMED
             |                                  |
             | pay decline (or bad input)       | pay again
             +--> stays PENDING_PAYMENT         +--> 400 "already paid"

   Receipt (showReceipt 2723) prints method, masked wallet, amount, transaction
   id and the demo disclaimer.

 6.4 Lookup later

   Lookup by phone -> GET /api/bookings?phone=09...
   getBookings (:200-212) normalises the phone, returns only matching bookings
   sorted newest first.
   An unpaid booking can be reopened and paid from the Bookings view.

 7. WORKFLOW C - HOTEL-OWNER PARTNER PORTAL
================================================================================

 7.1 Register / sign in

   Entry points: footer, Hotels menu, Hotels page CTA -> view-partner
   renderPartnerView (app.js:2835) -> renderPartnerAuth (2862) or dashboard.

   POST /api/partner/register   registerPartner (:214-244)
     ownerName >= 2 chars
     email matches name@host.tld
     phone normalised (09 + 7-9 digits)
     password >= 6 characters
     email must be unique (case-insensitive)
     account id "PT-" + 6 hex, createdAt timestamp
     password stored as salted SHA-256 in partnerHashes (never in Partner)
     savePartners() -> data/partners.ser; rolled back on failure

   POST /api/partner/login      loginPartner (:246-257)
     case-insensitive email lookup, verifyHash(), generic "no account" vs
     "password does not match" messages
   The returned Partner object (no password) is kept in localStorage
   (mstp.partner.v1) and its id is passed on every partner call.

 7.2 Dashboard

   renderPartnerDash (app.js:2909) loads in parallel:
     GET /api/partner/hotels?partnerId=PT-...
     GET /api/partner/bookings?partnerId=PT-...
   Shows property cards (rooms left, price, class), bookings for the partner's
   rooms, and simulated booking value.

 7.3 Publish / edit / remove a property

   openPartnerHotelModal (3040) -> submitPartnerHotel (3093)
   POST or PUT /api/partner/hotels  savePartnerHotel (:265-330)
     - caller must be a known partner (requirePartner)
     - name >= 3 chars
     - destinationId must exist in DataStore
     - pricePerNight 5,000 .. 5,000,000 MMK
     - rooms 1..300
     - tier Budget | Mid-range | Luxury (stars derived if omitted)
     - description >= 15 chars
     - new id "OWN-" + 6 hex, ownerId + ownerName stamped, rating 4.4,
       gradient derived from tier
     - update path requires partnerId == hotel.ownerId
     - DataStore.addPartnerHotel() or in-place update
     - savePartners() persists the whole PartnerData root

   DELETE /api/partner/hotels?partnerId=&id=
     deletePartnerHotel (:332-346): ownership checked, removed from DataStore,
     persisted.

 7.4 How a partner hotel reaches customers

   DataStore keeps one hotel list: the 27 built-in hotels plus every partner
   hotel added at runtime (and reloaded from partners.ser at startup).
   Therefore GET /api/hotels and /api/hotels?destinationId= immediately include
   the new property, the itinerary Hotels tab and the recommended hotel pick it
   up, and the booking flow can sell it. Partner rows carry ownerId/ownerName,
   which the UI renders as a "partner" badge and "Listed by ...".

   Demo account (seeded when -Dmht.demo=true):
     partner@mstp.demo / partner123  -> two Bagan sample properties

 8. WORKFLOW D - CULTURAL MARKETPLACE (CLIENT-SIDE ONLY)
================================================================================

 IMPORTANT: the shop never talks to the Java server. There is no /api/products,
 /api/cart, or /api/orders endpoint. All catalogue data ships in shop-data.js and
 all basket/order state lives in localStorage. A request to /api/products returns
 the SPA HTML because unknown extension-less paths fall back to index.html.

 8.1 Browse
   Shop views: shop, product, collection, cart (switchView 3684).
   shopData (3189) indexes products by id, destination collection, artisan,
   category, season; shopFiltered (3239) applies search + filters;
   shopCard (3267) renderShop (3301) renderShopGrid (3370).
   openProduct (3401) renderProduct (3412) - gallery, sizes, colours, quantity,
   artisan story, representative-photo + reference-price disclaimer.
   openArtisanModal (3607) shows the artisan profile.

 8.2 Cart
   addToCart (3496) stores { productId, size, colour, qty } in
   mstp.shop.cart.v1; renderCart (3511) recomputes lines and subtotal;
   shipping is a fixed 5,000 MMK (SHOP_SHIPPING).

 8.3 Checkout (a local draft, not an order)
   submitCheckout (3568) validates recipient name, phone, full address (>=10
   chars) and city, then writes a DRAFT record to mstp.shop.orders.v1:
     { id: "DRAFT-...", createdAt, items, subtotal, shipping, total,
       delivery: { city, method }, status: "DRAFT" }
   The name, phone and address are deliberately NOT stored.
   It clears the cart and toasts "Draft saved locally. No order was placed and
   no payment was taken."
   renderOrderHistory (3550) lists drafts (max 20 kept).

================================================================================
 10. DATA AND PERSISTENCE
================================================================================

 Runtime files (git-ignored):

   data/bookings.ser    HashMap<String, Booking>            written by pay/create
   data/partners.ser    PartnerData { partners, hashes, hotels }  written by
                        every partner write
   data/*.ser.bak       manual/previous copies, not read by the app
   lib/*.jar            PostgreSQL driver, HikariCP, SLF4J (only for db track)
   out/                 compiled classes

 Write discipline: writeAtomically(target, value, label)   (TripServiceImpl:469)
   serializes to a temp file, then atomically moves it over the target, so a
   crash cannot truncate bookings or partner data.

 Fail-safe read: if a .ser file cannot be deserialized, the file is preserved
   instead of being overwritten and the subsystem is flagged unhealthy
   (bookingsHealthy=false); every later save then fails with a clear message
   telling the operator to restore a backup and restart. (failSafe :559)

 Inventory rebuild: loadBookings() subtracts every stored booking's rooms from
   the in-memory hotel stock, so roomsLeft is consistent across restarts.

 Catalogue rebuild: DataStore recreates 9 destinations / 66 attractions / 27
   hotels on every start, then re-attaches partner hotels from partners.ser.
   Current live catalogue after the demo seed: 29 hotels.

 Booking record fields: id, hotelId, hotelName, destinationName, guestName,
   phone, checkIn, checkOut, nights, rooms, pricePerNight, total, status,
   paymentMethod, transactionId, paidAt, createdAt.

================================================================================
 11. SERVER VALIDATION MATRIX
================================================================================

 Itinerary          destinations 1..6, nights each 1..10, total <= 21,
                    adults 1..20, children 0..10, pace/hotelTier
                    whitelisted (unknown -> default, not an error), interests
                    free text; transport is neither required nor read
 Booking            guest name >= 2, Myanmar phone, nights 1..30, rooms 1..10,
                    rooms <= stock, check-in not in the past
 Payment            booking exists, not already paid, method in
                    {KPAY, WAVEPAY, AYAPAY}, wallet phone valid
 Partner register   owner >= 2, email regex, unique email, phone valid,
                    password >= 6
 Partner login      email must exist, password hash must verify
 Partner hotel      name >= 3, destination exists, price 5,000..5,000,000,
                    rooms 1..300, tier whitelist, description >= 15,
                    ownership on update/delete
 Partner queries    requirePartner: unknown partnerId -> 400
 Lookup             phone normalised; invalid phone -> 400

 Every failure becomes TripException -> HTTP 400 {"error":"human sentence"},
 never a stack trace; the UI shows it inline (form error) or as a toast.

================================================================================
 12. MONEY MODEL (all integer MMK)
================================================================================

 Stays       hotel.pricePerNight * nights * rooms, per destination
             (cheapest listed hotel in the requested class, fallback cheapest
             available; ceil(travellers/2) rooms; last stop loses one night)
 Total       sum of Stays. estTotal == estStay, always.

 There is no entry-fee, food, activity, shopping or transport expense: those
 figures are neither computed nor displayed, so nothing can leak into the total.
 Stay class changes the price; interests only change which attractions are
 scheduled. The marketplace shipping fee is a separate,
 client-only draft and never enters a trip total.

================================================================================
 13. ERROR AND OFFLINE BEHAVIOUR
================================================================================

 * Server down / wrong origin -> api() catches the network error,
   showServerOffline() displays a persistent banner explaining that the RMI
   server is not running, and a toast says so. The app does not pretend to have
   empty data.
 * Wrong method          -> 405 {"error":"Method not allowed"}
 * Bad JSON body         -> 400 with a parse error
 * Business rule failure -> 400 with the TripException sentence
 * Unknown destinationId  -> 400 "Unknown destination: x"
 * Missing static file   -> index.html (SPA); API paths never fall through by
                           accident because each route is registered explicitly
 * Port busy             -> gateway walks 8080..8099 and prints the chosen port
 * RMI not ready         -> WebMain retries the lookup 20 times (0.5 s apart)
 * Unreadable .ser       -> subsystem locked read-only with a clear console
                           warning instead of silent data loss
 * Shop                   -> every action is local; failures are form-level only

================================================================================
 14. SECURITY POSTURE (demo, not production)
================================================================================

 Present:
   * CSP, X-Frame-Options DENY, nosniff, no-referrer, Permissions-Policy,
     HSTS, request ids, X-Content-Type-Options
   * Path traversal blocked in staticFile(); web root pinned
   * Partner passwords salted + SHA-256, never returned to the client
   * No PIN collection, payments explicitly simulated and labelled
   * Server-side validation of every business field (never trusts the form)
   * Atomic writes + fail-safe reads for data files
   * Shop checkout deliberately does not persist name/phone/address

 Known weaknesses (documented in docs/SECURITY_AUDIT.md):
   * No traveller accounts or sessions; profile is browser-local
   * Partner APIs trust a client-supplied partnerId (no session token)
   * Booking lookup by phone number is unauthenticated
   * Inventory is a single counter, not per-date
   * .ser storage has no encryption or access control
   * Do not expose this build to the internet or enter real personal data

================================================================================
 17. KNOWN GAPS / ROADMAP
================================================================================

   * PostgreSQL is designed and migratable (db/, DATABASE_SCHEMA.sql, SerExport)
     but the RMI service still reads/writes .ser - wiring is Phase 1C/1D.
   * No traveller accounts, sessions, RBAC, or admin dashboard.
   * Room inventory is one counter, not per-date availability.
   * Marketplace has no backend: no stock, no orders, no payment, no shipping.
   * Weather and route-plan endpoints proxy to an external engine that is not
     part of this repository (defaults to 127.0.0.1:8000).
   * Payments are simulated; no provider integration.
   * No notification service, audit log, or rate limiting.
   * Destination facts, fees, and opening times are curated demo data, not live
     supplier data.
